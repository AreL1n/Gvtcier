前置 - 游戏基础

在正式开始做游戏前，我们先来了解 Gvtcier 引擎。

Gvtcier 是由 Li-HuaL1n 软件开发的一个以中文为主的 3D 引擎，能进行一些有趣的游戏制作。

Gvtcier 引擎通常使用 Gvts 格式的文件来执行游戏指令，你可以创建一个这样的文件，在里面写下游戏的逻辑。

那么地图呢？有两个方法。一个是麻烦的：你需要在 Gvts 脚本文件内创建这些几何体，对于大型游戏这太痛苦了。所以，你可以试试 Gmap 文件，这是 Gvtcier 引擎的地图文件，详见教程中的 Gmap 章节。

同时，我们将游戏包裹为一个 gpk 文件，你可以使用我们提供的工具进行编译。它是跨平台的，你可以在 Windows（窗户）和 Android（安卓）系统中使用它，它只需要一个用于启动它的 exe，这不需要你负责。

前置 - 编程的概念

这一章不讲任何引擎功能，只讲「编程」这件事本身。已经写过代码的读者可以跳过；从零开始的读者请先读完这一章，后面所有章节的表格才有意义。

程序是什么

程序就是一份按顺序执行的指令清单。引擎从第一行读到最后一行，读到什么做什么：读到求和就算和，读到画图就画图，读到判断就走其中一条路。游戏脚本特殊的地方在于它不是「从头跑到尾就结束」，而是围绕几个固定的入口反复运行——比如 当三维开始时（或二维游戏用的 当二维开始时）里写的代码每帧都会被引擎调用一次，一秒约六十次。你写的不是一份跑完就扔的说明书，而是一套「每次被问到就回应一下」的规则。

变量 —— 给值起名字

变量是一个有名字的盒子，用来把一个值存起来，供后面的代码使用。声明就是「造盒子并放入初值」：

局部 生命值 = 100;
全局 分数 = 0;

局部 的盒子只在当前这块代码里存在，出了这对花括号就消失；全局 的盒子整个脚本都活着，跨帧不丢。往盒子里放新值叫赋值，直接写名字 = 新值即可，不需要再写 局部：

生命值 = 生命值 - 10;

右边的表达式先算出来，再放进左边的盒子。所以这句话的意思是「取出 生命值 里的数，减 10,放回 生命值」——数学上看不成立，程序里是每秒都在发生的事。

值有不同类型:数字(100、0.5)、字符串("敌人")、布尔(真 / 假)、空(空)。类型决定能做什么运算：数字能加减，字符串能拼接，布尔能配 如果。Gvts 是动态类型语言，盒子上不写类型，一个盒子先装数字后装字符串也可以，但请保持每个变量类型稳定，否则读代码的人会迷失。

函数 —— 把一段操作打包复用

函数是给一段代码起名字。把常用的操作写进函数，以后每次只喊名字就能执行整段：

函数 扣血(数量) {
    生命值 = 生命值 - 数量;
    执行_打印(生命值);
}

扣血(10);
扣血(30);

括号里的 数量 叫参数：调用时传进来的值会在函数内部当作变量用。调用 扣血(10) 时 数量 就是 10,调用 扣血(30) 时就是 30——同一段代码，不同输入，不同结果。返回 负责把函数算出的结果交还给调用处：

函数 加(a, b) { 返回 a + b; }
局部 总分 = 加(2, 3);

没有 返回 的函数执行完就结束，交回 空。函数的意义在于消除重复:同一件事写一遍、起名字、到处用；要改逻辑时只改一处。

句柄 —— 代表远处对象的凭据

变量通常装「值」(数字、字符串)，但游戏里很多操作的对象不在你的代码里，而在引擎的场景中——某个敌人、某扇门、某盏灯。代码没法把整个 3D 物体塞进一个变量，于是引擎给你一个句柄:一张代表那个对象的凭据。

局部 门 = 获取_实体("大门");
设置_属性(门, "位置Y", 3);

变量 门 里存的不是门本身，而是「通往场景里那扇门的凭据」。拿着句柄调用 设置_属性 / 移动_实体 等关键字，引擎就凭据找到真身去执行。句柄的特征：

· 它可能失效。对象被删除后，手里这张凭据就成了空头支票，再用会得到 空 或报错。所以句柄变量用前要判断是否为 空。

· 它是引用，不是拷贝。十个变量装同一把句柄，指向的是同一个物体；通过任何一个改动，大家都看得见。

· 句柄和值的区别，决定了「改变量」和「改对象」是两件事：生命值 = 100 改的是你自己的盒子；设置_属性(门, ...) 改的是场景里的门。

花括号 —— 代码的领土边界

花括号 { } 圈出一段代码的从属范围(术语叫作用域或块)。它回答两个问题：这段代码归谁管、里面的名字活多久。

如果 得分 > 100 那么 {
    执行_打印("升级");
    等级 = 等级 + 1;
}

{ 后面的每一行都听 如果 的：条件成立，块里的代码全部执行；不成立，整块跳过。块可以嵌套——大块里套小块，像地图上的国界套省界：

循环 i=1,3 执行 {
    局部 提示 = "第" + i + "轮";
    如果 i == 2 那么 {
        执行_打印(提示);
    }
}

内层块能用外层块声明的 提示(省界在国界之内，合法)；反过来外层看不到内层的东西。一个 局部 变量从声明它的 { 开始，到配对的 } 结束——这就是它的寿命。

为什么习惯写成 换行 + 花括号独占一行

下面的两种写法，引擎看来完全一样：

代码 {
    内容
}
代码 {}

但人读起来天差地别，原因有三：

一、对齐即逻辑。左花括号 { 单独跟在引语后面，右花括号 } 独自回到与引语对齐的位置，一对括号把「归谁管的内容」看得清清楚楚。扫一眼竖着对齐的 } 就能数出层级；全部挤在一行里，嵌套三层后没人能一眼认出哪个 } 配哪个 {。

二、错误更醒目。少写一个 } 时，独占一行的排版里空白会出卖它——某一块明显没有收尾；挤在一行里，少一个括号混在字符堆里几乎不可能靠肉眼发现。

三、增删安全。往块里加一行，新行自己占一行，不会动到别的行；挤在一行里每次修改都在动同一条物理行，多打一个分号、少打一个括号都直接破坏整句。

所以约定如下：引语(如果 / 循环 / 函数 ……)+ 空格 + { 换行；块内每行缩进一层(四个空格)；} 单独一行，与引语首字对齐；每条语句以分号结尾。这不是语法强制——本引擎零缩进也能跑——而是让代码对「三个月后的你」和「其他读者」可读的纪律。

表达式与运算符 —— 任何能算出一个值的写法

前面说「右边的表达式先算出来」。表达式就是任何能算出一个值的写法:1 + 2、生命值 - 10、"第" + i + "轮"、加(2, 3) 都是表达式。运算符按优先级结合：先算 * / %（乘、除、取余），再算 + -，然后比较 > < >= <= == ~=，再然后 且，最后 或。同级从左到右。== 判断相等，~= 判断不等；// 是整除不是注释，注释只用 --。字符串用 + 拼接，.. 在本引擎里不表示拼接。括号 ( ) 可以强行改变顺序，读不懂优先级时就加括号，不要赌记忆。

真值与假值 —— 如果 判断的不只是 真 假

如果 / 当 / 且 / 或 / 非 接受的不只是 真 假：假 和 空 为假，其余一切（包括 0、空字符串、空表）在本引擎里都按真处理。所以判断「变量有没有值」要用 == 空 或 ~= 空，不要写 如果 变量 那么 来指望它替你把 0 也当假。条件表达式的结果永远是 真 或 假，可以直接存进变量：

局部 可以开门 = 有钥匙 且 有电;

表 —— 一个盒子装一组盒子

前面只讲了装单个值的变量。表（table）是能装任意多个值的容器，用 { } 构造，两种用法：数组用序号 1、2、3… 访问，字典用键访问。

局部 背包 = { "钥匙", "地图" };   局部 第一件 = 背包[1];
局部 属性 = { 速度 = 3, 名称 = "敌人" };   局部 速度值 = 属性.速度;

表的序号从 1 起，不是 0。表是引用类型，和句柄一样：局部 甲 = 某表; 局部 乙 = 甲; 改 乙 就是改 甲，要复制得逐项搬。遍历数组用 数组遍历，遍历键值对用 遍历，新增 表.插入，删除 表.移除，长度用 #表 或 原始长度。表和句柄最容易混：表是你自己在脚本里造的盒子，句柄是引擎发给你的凭据，两者都不能用 == 直接比较内容，只能比较是不是同一个。

函数进阶 —— 传值、传引用与把函数当值

参数按值传入：数字、字符串、布尔传进去的是副本，函数里改不影响外面；表、句柄传进去的是引用，函数里改内容外面看得见。函数可以没有 返回（交回 空），可以返回多个值（返回 a, b，调用处 局部 甲, 乙 = 函数() 接住），也可以当作值传给别的函数（执行_命令(函数名)、保护调用(函数, ...) 就是这种用法）。定义在 当三维开始时（或 当二维开始时）块里的函数每帧都会被重新定义一次，所以函数体内不要依赖「只执行一次」的初始化；真正的初始化用帧号标志位守住。

错误与断言 —— 错了就立刻停下

出错不可怕，可怕的是错了还继续跑。报错("消息") 主动抛出，断言(条件, "消息") 条件不成立就抛，保护调用 把可能出错的调用包起来、成功返 真 加结果、失败返 假 加错误，警告(...) 只提示不中断。凡是「这一步不成立后面全错」的地方，都该断言；凡是「外面给的数据可能不合法」的地方，都该保护调用。

执行顺序与分帧 —— 每帧从头重跑

代码是从上往下执行的，但主循环每帧从头重跑。这意味着：本帧写在后面的代码，看到的是本帧前面代码改过的值；下一帧再跑时，局部变量已经没了，只有 全局 还在。所以「只做一次」的事要靠帧号标志位守住，「每帧都做」的事直接写在块里，「过一会儿再做」用 执行_等待（它挂起的是当前函数剩余的代码，不冻结引擎，也不冻结别的函数）。时序上最容易犯的错是把初始化写在了每帧都会跑到的位置，于是物体被反复新建、音效被反复加载——看到「东西越来越多」或「声音叠在一起」，先查这里。

命名与读代码 —— 名字是写给人的

变量名写清楚它装什么（剩余血量 比 a 好），函数名写清楚它做什么（扣血 比 处理 好），一个函数只做一件事。句柄用前判 空，表用前判是不是表，数字用前判类型；类型(值) 返回 "number"、"string"、"table" 这类字符串，配合 如果 用。缩进、换行、花括号独占一行，不是为了引擎，是为了三个月后的你——这一章开头讲过，这里再重复一次，因为它是后面三十几章唯一不需要记、却最影响你能不能读懂自己代码的纪律。

把这一章收拢成几句话

变量、函数、句柄、表、花括号，加上表达式和真值判断，就是这门语言全部的「零件」。后面每张表里的关键字，拆开看都只是这些零件的组合：参数是值或句柄，返回值是值或句柄，块是花括号，回调是函数。遇到看不懂的写法，回到这一章拆开它——拆不动，说明缺的是上面某一条，而不是引擎太难。

困难 - 三十二 用 C++ 给游戏编写 UI

前面所有章节都用 Gvts 脚本做事。但脚本的绘制能力是有限的：它擅长画矩形、文字、图片，适合做游戏内的 HUD 与菜单，却画不出完全自定义的控件外观与精细交互。当你要的是「一套自己的界面」——圆角按钮、自绘边框、拖动条、虚拟摇杆——可以在 Demo 目录里写一个 C++ 文件，让引擎在每帧渲染结束后回调你，由你用引擎的 2D 绘制接口把界面画上去。这一章讲的就是这条通路。

覆盖层是什么

引擎在安卓入口处预留了两个弱符号。所谓弱符号，就是「引擎声明了它、但不要求你一定实现」：你实现了，引擎就调用你的；你不实现，引擎用一个空的默认版本，一切照常。它们让界面代码留在你的 Demo 里，而不必改引擎。

弱符号作用签名
Gvtcier_Android_DrawOverlay每帧渲染完成后回调，用来绘制界面void Gvtcier_Android_DrawOverlay(Renderer& r, const GvWWindow* w)
Gvtcier_Android_AppName返回应用标题，缺省为 "Gvtcier"const char* Gvtcier_Android_AppName()

Gvtcier_Android_DrawOverlay 的调用时机很关键：它在场景渲染完、2D 画布结束帧之后、交换缓冲区之前触发，因此你画上去的内容一定盖在所有游戏画面之上，正是界面该在的层级。

把文件放进 Demo

在你的 Demo 目录下新建一个名为 android_main.cpp 的文件，Android 构建脚本会自动发现并编译它，无需改任何构建配置。文件名固定，不能换成别的名字。

画出第一个按钮

引擎的 Renderer 提供了四个屏幕像素坐标系的 2D 接口，界面全靠它们拼出来：

接口用途
Gvtcier_Render_DrawRect2D(x, y, 宽, 高, R, G, B, A, z)画一个填充矩形，坐标为屏幕像素，z 越大越靠前
Gvtcier_Render_DrawText(x, y, 缩放, 文本, z, R, G, B, A)画一行文字，xy 为左上角，缩放为字号倍率
Gvtcier_Render_MeasureText(文本, 缩放, 出宽, 出高)先量出文字像素尺寸，用于居中与做热区

下面是一段最小实现：在屏幕左下角画一个半透明方块。窗口尺寸从回调参数 w 里取，这样不同分辨率下都能摆对位置。

#include "render/renderer.h"
#include "platform/gvw.h"

extern "C" __attribute__((visibility("default")))
void Gvtcier_Android_DrawOverlay(Renderer& r, const GvWWindow* w) {
    if (!w) return;
    float s = 160.0f;
    float x = 32.0f;
    float y = w->height - 32.0f - s;
    r.Gvtcier_Render_DrawRect2D(x, y, s, s, 0.2f, 0.5f, 0.9f, 0.75f, 900);
}

让按钮有交互

界面要能响应输入。C++ 侧靠 GvW_IsKeyDown(w, 键) 查询按键状态，它接受字符：W A S D 与空格分别对应前、左、后、右与跳跃。判断是否在某个矩形内则用坐标比较。把二者合起来，就能做出「按下时高亮」的按钮——位置同时喂给绘制与命中判定，保证视觉与热区完全重合。

#include "render/renderer.h"
#include "platform/gvw.h"

namespace {
const float kMargin = 24.0f;

struct Rect { float x, y, w, h; };

bool inRect(const Rect& r, int px, int py) {
    return px >= r.x && px < r.x + r.w && py >= r.y && py < r.y + r.h;
}

void drawKey(Renderer& r, const Rect& rc, const char* label, bool down) {
    if (down) r.Gvtcier_Render_DrawRect2D(rc.x, rc.y, rc.w, rc.h, 0.95f, 0.85f, 0.35f, 0.95f, 900);
    else      r.Gvtcier_Render_DrawRect2D(rc.x, rc.y, rc.w, rc.h, 0.10f, 0.12f, 0.16f, 0.55f, 900);
    float tw = 0, th = 0;
    r.Gvtcier_Render_MeasureText(label, 2.0f, &tw, &th);
    r.Gvtcier_Render_DrawText((int)(rc.x + (rc.w - tw) * 0.5f),
                              (int)(rc.y + (rc.h - th) * 0.5f),
                              2.0f, label, 901);
}
}

extern "C" __attribute__((visibility("default")))
void Gvtcier_Android_DrawOverlay(Renderer& r, const GvWWindow* w) {
    if (!w) return;
    float s = w->height / 5.0f;
    Rect jump = { w->width - kMargin - s * 1.5f, w->height - kMargin - s * 1.5f, s * 1.5f, s * 1.5f };
    drawKey(r, jump, "跳", GvW_IsKeyDown(w, ' '));
}

和触摸的关系

你也许注意到上面只查了键盘状态，没有自己处理触摸。原因是安卓的触摸事件已经由引擎转成虚拟按键：引擎在 gvw_android.cpp 里维护了一套屏幕坐标下的按键热区，手指按下后刷新对应的键状态，GvW_IsKeyDown 再去读它。因此你只要在同样的坐标画按钮，点击就会自动落到你画的地方。这也解释了为什么按钮「能点却没显示」时，问题一定出在绘制侧——热区在引擎里，绘制在你这。

几个要点

1. 回调每帧触发一次，函数体要轻，别在里面做重活；界面状态尽量用静态变量或全局变量缓存。

2. 所有坐标是屏幕像素，锚点用 w->width / w->height 相对计算，才能适配不同尺寸的屏幕。

3. z 值决定前后层级，界面统一用一个大数（如 900 以上），保证盖过游戏内 HUD。

4. 需要文字居中、控件自适应宽度时，先用 Gvtcier_Render_MeasureText 量尺寸，再算位置，别写死像素。

困难 - 三十三 模组（.glc）

模组是给已经发布的游戏做扩展的独立包，扩展名 .glc。它不需要游戏作者预留任何接口，也不需要重新打包主包：把模组文件放进游戏目录的 mod 子文件夹，启动时引擎自动加载。

放在哪里

路径说明
Games/<游戏ID>/<游戏名>.gpk主游戏包，一个目录一个
Games/<游戏ID>/mod/<模组名>.glc模组包，可放多个
Games/<游戏ID>/mod/<模组名>.glc.disabled同名的空文件，放了它这个模组就被跳过

多个模组按文件名升序依次加载，后加载的优先。想让某个模组最后生效，就在名字前面加数字前缀。

同名文件谁生效

查找顺序是 模组 → 主包 → 磁盘，谁在前谁生效。所以模组里放一个和主包同名、同路径的文件，就等于把这个文件换掉了；模组里独有的文件则是纯新增。这条规则对所有资源一视同仁：贴图、模型、音频、特效 JSON、gmap 地图、被 包含 的子脚本，甚至主脚本 game.gvts 本身。

想做的事模组里放什么
换掉一张贴图同名的 .png
换掉整张地图（含天空、环境光、模型摆放）同名的 .gmap
只改一行文字或配色根目录 mod.ghook，每条写「替换 "原文" 为 "新文"」
只换某个函数的实现_override/<函数名>.gvts，内容就是新的函数体
改玩法机制（整份接管）同名的 .gvts 子脚本；或者直接放一份 game.gvts 把主脚本换掉
在主脚本的时机插自己的代码根目录 _mod.gvts，定义 钩子_载入 / 钩子_每帧 / 钩子_绘制
只加内容不改原内容主包里没有的新文件，由主包脚本按名字去取

打包一个模组

在模组目录里放一个 mod.json 作为身份信息，其余文件按你希望它们被游戏看到的路径摆放：

{
    "name": "绿色天空",
    "version": "1.0",
    "author": "你的名字",
    "description": "把天空和环境光换成绿色"
}

然后把整个目录打成 .glc，产物会自动放进目标游戏的 mod 文件夹：

python build.py -mod <模组目录> --game <游戏ID>

省略 --game 时，如果 Games 下只有一个游戏目录就自动选中，否则要求显式指定。打包白名单为 json / png / wav / mp3 / obj / glb / txt / mp4 / gvts / gmap / ghook。

只写差异，别把整个游戏拷进模组

模组最轻的形态只携带差异。三种力度从轻到重：

形态放什么生效方式
mod.ghook一条条「替换 "原句" 为 "新句"」在主脚本原文里做文本替换，只换掉那一段字符，脚本其余部分仍是主包的
_override/<函数名>.gvts新的函数体，不带函数头按函数名整块替换，主脚本其他函数照旧跟随主包更新
game.gvts整份主脚本整体接管；主包以后改机制时，模组不会自动跟上

想插自己的逻辑又不改主脚本，就在 _mod.gvts 里写 钩子_载入、钩子_每帧、钩子_绘制 三个函数中的任意几个。它们在主脚本的对应时机被调用，和主脚本共用全局量，因此可以直接给原变量赋值。

怎么找到自己要改的那一处

不要凭空猜名字。先用 列出_全局("关键词") 看有哪些全局量、各自是什么类型，把范围缩小；再用 获取_能力列表() 与 查询_能力("片段") 确认某个能力叫什么、怎么用。

片段覆盖的文件名必须与函数名一字不差。ghook 的「原句」必须与主脚本那一行完全一致，空格与分号都算；对不上时日志会留一行「补丁未命中」，照着这句话回去核对原文即可。

示例：绿色天空

Bloor 例子的世界天气写在地图里。把地图拷一份到模组目录，只改世界块的颜色，其余行原样保留：

世界 {
天空 0.24 0.86 0.34
环境光 0.62 0.95 0.66 0.22
太阳 0.34 -0.62 0.50
太阳颜色 0.86 1.0 0.86
雾 0.0036
重力 30
}

打成 绿色天空.glc 放进 Games/Bloor/mod/，启动 Bloor 就是绿色天空，主包一个字节都没动。启动器 Bloor 的详情页也会多出一行「此游戏包含 1 个模组」。

出错了会怎样

模组文件损坏、版本不认识、校验值不符时，这一个模组会被整体跳过并在日志里留一行，游戏照常启动。模组里写的脚本有语法错误时，报错行号指向模组里的那份脚本，和平时改主脚本的体验一致。
